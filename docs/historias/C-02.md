## 1. Historia · *Planificador*
**Como** usuario **quiero** iniciar y cerrar sesión y recuperar mi contraseña **para** usar mi cuenta en cualquier dispositivo.

Descripción en Notion: «El usuario inicia y cierra sesión y puede recuperar su contraseña por correo. La sesión se mantiene al volver a abrir la app.» · Requisitos: RF-01, RNF-12 · Épica EP-01 · Prioridad Must · v1.0 MVP · Actividad «1. Unirme a la comunidad».
Trazabilidad en Notion: «Domain: IniciarSesionUseCase · Backend: auth».

**Criterios de aceptación** (copia literal de Notion, página editada el 2026-11-07):
- CA-1 Sesión persiste al reabrir la app
- CA-2 Recuperación por correo
- CA-3 Cerrar sesión limpia datos locales
- CA-4 Persistir la revocación pendiente de cierre de sesión y reintentarla al recuperar red (criterio del PO, 2026-11-06; viene de SP-04 H-6)
- CA-5 Android: un `IOException` real al leer la sesión (`AlmacenDeSesionCifrado.leer()`, `datos.data.first()`) devuelve `null` sin `borrarTodo()` y no cierra la app al abrir (SP-04 H-20)
- CA-6 Cerrar sesión sin red funciona también cuando falla la consulta `avisoAceptado` al rechazar el aviso: la sesión local se cierra y el error se propaga. Se agrega un caso a CP-164g con la consulta fallida, con el mismo ID en Swift y Kotlin (C-01 H-16, decisión del PO del 2026-11-07)
- CA-7 Si falla la revocación del aviso de privacidad, la sesión se cierra igual y la revocación queda pendiente en el dispositivo. Se reintenta al recuperar la red o en el siguiente arranque, antes de cualquier otra acción (decisión del PO del 2026-11-07; hoy C-01 no la guarda, ver CP-164g)
- CA-8 Enlace de verificación inválido o expirado: pantalla con «Este enlace ya no es válido o expiró» y botón «Reenviar correo» (`ReenviarVerificacionUseCase`), sin detalles técnicos. Si la app se abrió en frío y no tiene el correo, lo pide (decisión del PO del 2026-11-07; hoy C-01 muestra «Abre el enlace en este teléfono o pide uno nuevo»)

### Estado actual del repo (punto de partida, `feat/C-01-registro-de-usuario` 6f657d7)
- **Domain `Cuentas`:** `IniciarSesionUseCase(.google)` (sin correo), `ObtenerSesionActualUseCase`, `CerrarSesionUseCase` (borra lo local y después `try? revocarSesionEnServidor()`, P-8), `RechazarAvisoDePrivacidadUseCase(repositorio:cerrarSesion:)` (consulta → revoca → cierra; propaga el `ErrorDeConsentimiento`), `HayQuePedirElAvisoAlArrancarUseCase`, `ReenviarVerificacionUseCase`, `ConfirmarCorreoUseCase`. Puertos `RepositorioDeSesion` (`iniciarSesion(con:nonce:)`, `sesionActual`, `borrarSesionLocal`, `revocarSesionEnServidor`), `RepositorioDeConsentimiento` (`aceptarAviso`, `avisoAceptado`, `revocarAviso`), `RepositorioDeRegistro`. `ErrorDeAutenticacion`: `cancelado`, `credencialRechazada`, `sinConexion`, `configuracionIncompleta`, `desconocido`.
- **Data:** `RepositorioDeSesionSupabase` guarda el access token **solo en memoria** entre `borrarSesionLocal` y `revocarSesionEnServidor` (`POST /auth/v1/logout?scope=local`; 401/403/404 cuentan como revocada). Si no hay red, el token se pierde y la sesión del servidor sigue viva (SP-04 H-6). Si el access token venció, el logout da 401 y el refresh token sigue vivo. `AlmacenDeSesionKeychain` (servicio `<bundle>.sesion`) y `AlmacenDeSesionCifrado` (Tink + DataStore `sesion`, con parámetros `nombre` y `aliasDeLlave`). En Android, `leer()` tiene `datos.data.first()` fuera del `try` (H-20).
- **Presentation / App:** `AccesoView/Screen` (SP-04): con sesión muestra el usuario y «Cerrar sesión» (sin confirmación); sin sesión, solo Google. «Ya tengo cuenta» en Bienvenida lleva a Acceso (P-10 de C-01). `ErrorDeRegistro.enlaceInvalido` se muestra como texto en Verifica tu correo («Abre el enlace en este teléfono o pide uno nuevo»). Navegación en `ios/RugbyApp/Cuentas/NavegacionDeCuenta.swift` (`PasoDeCuenta`) y en `MainActivity.kt` (rutas `RUTA_*`).
- **Backend:** `config.toml` con `[auth.rate_limit] sign_in_sign_ups = 30` (por IP cada 5 min; en Supabase cubre altas **e inicios de sesión**), `token_refresh = 150`, `minimum_password_length = 10`, `additional_redirect_urls = ["rugbyapp://auth-callback"]`. La RPC `revocar_aviso_de_privacidad(p_version)` es idempotente: si el aviso no está vigente devuelve `false` y no guarda nada.

### 3.5 Decisiones que requieren ADR
- **ADR 0010 · Revocaciones pendientes** (nuevo, depende de P-3): para revocar la sesión o el aviso después de borrar la sesión local hace falta una credencial del usuario (el logout exige su JWT y la RPC usa `auth.uid()`). Decisión propuesta: guardar el **refresh token** (no el access token, que vence en 1 h y deja el logout en 401: SP-04 H-6) en una entrada aparte del almacén seguro, por `usuarioId`, que el cierre de sesión no borra; reintentar con refresh → RPC → logout. Alternativas descartadas: (a) token solo en memoria (hoy; pierde la revocación sin red); (b) guardar el access token (vence; no revoca el refresh); (c) revocar desde una Edge Function con `service_role` (más superficie y un endpoint que acepte «revoca a X» sin la credencial de X). Consecuencia: «Cerrar sesión limpia datos locales» deja una única excepción documentada.
- **ADR 0008 · Enlace de verificación de correo** (se actualiza): segunda Redirect URL exacta `rugbyapp://recuperar-contrasena` (en lugar de distinguir por estado en memoria, que se pierde en frío, o por parámetros en la URL, que Supabase compara contra la lista blanca); path vacío obligatorio en los dos enlaces (C-01 H-1); la pantalla de CA-8 reemplaza el texto «Abre el enlace en este teléfono o pide uno nuevo».
- El `.pbxproj` no se toca (ADR 0004): no cambian `Info.plist` ni `project.yml` (el esquema `rugbyapp` ya está registrado; el host nuevo no necesita registro en iOS).
